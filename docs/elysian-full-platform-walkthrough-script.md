# Elysian Full Platform Walkthrough

**Purpose:** Record the current Elysian product end to end before any Shobiz-specific pilot work begins.

**Recommended duration:** 24-28 minutes

**Presenter model:** One presenter can read every line. If two people present, Presenter 1 handles the opening, client, and closing; Presenter 2 handles vendor, operations, and admin.

**Truth rule:** Demonstrate only saved, working product behavior. Never show credentials, source code, cloud consoles, private vendor payouts to a client, or real client data.

## Recording Preparation

Use four anonymized accounts in separate browser profiles:

1. Client: a corporate event host with a three-day plan.
2. Vendor: a verified production or catering partner with services and catalogue items.
3. Operations employee: an active Manager-role account assigned to the sample event.
4. Administrator: an Admin-role account.

Prepare the sample event with:

- Event name: `Northstar Leadership Summit 2027`.
- Type: `Corporate Event`.
- Three days with dates.
- Functions such as `Executive arrivals`, `Leadership sessions`, `Awards evening`, and `Departure hospitality`.
- Different venues or rooms per function.
- Food, decor, photo/video, entertainment/production, hospitality, and logistics needs.
- Two selected vendor services.
- One menu, four tasks, logistics timings, guests, and a run of show.
- One published final client price and invoice.
- One open operations update and one urgent incident.

Recording settings:

- Record at 2560x1440 or 1920x1080, browser zoom 90-100%.
- Hide bookmarks, notifications, passwords, developer tools, and unrelated tabs.
- Use the same browser width throughout each portal.
- Pause for one second before every click and after every save.
- Record the screen first and narration second if live narration makes navigation rushed.
- Keep the pointer still while explaining a screen.

## 00:00-01:15 | What Elysian Is

**Account:** Signed out

**On screen:** Marketing home page.

**Action:** Scroll slowly through the opening sections, then stop before sign-in.

**Presenter 1:**

"Elysian is an event planning and live-delivery platform for weddings, conferences, corporate retreats, product launches, private celebrations, and other complex events.

It connects three phases that are usually split across chats, spreadsheets, documents, and separate vendor conversations. First, the host defines the event. Second, the host and Elysian compose every function, requirement, vendor service, guest need, and cost. Third, the operations team takes the approved plan into live delivery, records decisions and incidents, and carries a printable field book.

The same source of truth is viewed differently by clients, vendors, operations employees, and administrators. Access is role-based and event-scoped."

**Action:** Click `Sign In` and enter the client account.

## 01:15-04:30 | Client Layer 1: Define the Event

**Account:** Client

**On screen:** Client onboarding.

**Presenter 1:**

"Elysian does not assume every event is a wedding. The host explicitly chooses an event type before anything is created."

**Actions and narration:**

1. Enter `Northstar Leadership Summit 2027`.
   - Say: "The event name becomes the anchor across every portal."
2. Click `Continue`.
3. Select `Corporate Event`.
   - Say: "The platform also supports conferences, launches, retreats, performances, private dinners, festivals, hospitality events, weddings, and custom formats."
4. Select `3` days.
   - Say: "We define duration before detail, without asking the client to invent a budget. Elysian estimates spend after the plan has enough evidence."
5. Set each day date.
6. Open Day 1, then expand Morning, Afternoon, and Evening.
7. Rename blocks to `Executive arrivals`, `Leadership sessions`, and `Welcome dinner`.
8. Set time, expected guests, venue from the dropdown, and required workstreams.
9. Repeat quickly for Days 2 and 3.
10. Click `Create event & open planner` once.

**Presenter 1:**

"Nothing is created while we move between steps or press Enter inside a field. Creation happens only through this explicit final action. Each enabled block becomes a real function with stable identifiers, so vendors, menus, bookings, costs, tasks, and operations records remain attached to the correct function."

## 04:30-08:15 | Client Layer 2: Compose the Event

**On screen:** `Event Plan`, Layer 2 flowchart.

**Actions:**

1. Point to the event hub and day nodes.
2. Click Day 1.
3. Click `Leadership sessions`.
4. Point to its shaped step tokens.
5. Open `Basics`.
6. Show the event name, date, time, venue dropdown, guests, and notes.
7. Click `Back to steps`.

**Presenter 1:**

"Layer 2 is a map rather than one long form. The user moves from the event, to a day, to a function, and then opens only the step they need. The breadcrumb and selected branch keep the user oriented inside a large multi-day plan."

### Food and vendor-linked requirements

**Actions:**

1. Open `Food`.
2. Show the shortlisted vendor services first.
3. Select two services from one vendor if the prepared data supports it.
4. Add the selected catalogue rows to the menu.
5. Add one special requirement that requires a final offline price.
6. Save and continue editing without leaving the selected function.

**Presenter 1:**

"Vendors are not typed into untracked text fields. A requirement points to a real vendor profile and one or more real services. Catalogue rows show what the vendor actually offers. Standard priced items contribute to the estimate; a special request remains clearly marked for a final confirmed price."

### Design, logistics, tasks, and notes

**Actions:**

1. Open `Design`, select a setup, and save.
2. Open `Logistics`, then show load-in, guest arrival, transport, rooming, weather, and operating notes.
3. Open `Tasks`, add an owner and due date, then mark one task in progress.
4. Open `Notes`, add one function-specific instruction.
5. Return to the flowchart.

**Presenter 1:**

"Each concern is scoped to the chosen function. Saving a design setup does not throw the user back to the start. Tasks and logistics remain readable enough for the delivery team, while the map keeps the overall event compact."

## 08:15-10:00 | Client Layer 3: Finalize and Find Gaps

**Action:** Select Layer 3.

**Presenter 1:**

"Finalization is not a dead checklist. It reads the actual plan and surfaces what is complete, partial, or missing across structure, requirements, vendors, cost, guests, hotels, and run of show. The client can reopen any function, change a choice, and let readiness recalculate."

**Actions:**

1. Point to the overall readiness percentage.
2. Open one incomplete check.
3. Return to the relevant function step.
4. Complete the missing field and save.
5. Return to Layer 3 and show the updated result.

## 10:00-12:15 | Client Cost, Guests, Schedule, and Communication

### Cost estimation

**Action:** Open `Cost Estimation`.

**Presenter 1:**

"The client can inspect estimated spend by category or by event. The view separates planned, quoted, paid, due, and variance rather than showing one unexplained total. Event changes and cost planning share the same function references, so the budget does not become a detached spreadsheet."

**Actions:**

1. Switch between `By category` and `By event`.
2. Show the summary and one event card.
3. Reassign a line item to the correct function.
4. Save changes.

### Guests and run of show

**Actions:**

1. Open `Guests`.
2. Add a guest to `Host A`, set RSVP and meal preference, and show seating view.
3. Open `Run of Show`.
4. Show the three-day schedule and one function task.

**Presenter 1:**

"Guest groups are host-neutral, so corporate and private events do not inherit bride-and-groom assumptions. The run of show turns the event map into a chronological execution view."

### Vendors, bookings, billing, and messages

**Actions:**

1. Open `Vendors`; filter by category and open a profile.
2. Show scope, inclusions, deliverables, add-ons, itemized catalogue, and media.
3. Show shortlisted state and the next action.
4. Open `Bookings` and one booking detail.
5. Open `Billing`; show only the published client total, invoice, received amount, and due amount.
6. Open `Messages`; choose the booking conversation and point to the event context rail.

**Presenter 1:**

"The client sees the complete published price collected by Elysian. Vendor payout and Elysian fee remain private. Messages stay attached to the booking, service, function, date, and venue rather than becoming an isolated inbox."

## 12:15-15:15 | Vendor Portal

**Account:** Vendor

**Action:** Sign out and sign in as the sample vendor.

**Presenter 2:**

"The vendor portal turns a listing into an operating profile. The vendor manages what clients can discover and what the delivery team can rely on."

**Actions:**

1. On the dashboard, show bookings, inquiries, profile views, rating, paid-to-date, and outstanding payout.
2. Open `Profile`; show business coverage, description, and public identity.
3. Open `Services`; edit one service.
4. Show service scope, event fit, inclusions, deliverables, add-ons, catalogue rows, ordering controls, and item media.
5. Open `Portfolio` and show the public visual references.
6. Open `Inquiries`; open the prepared event brief.
7. Open `Bookings`; show the event, service, status, and vendor payout ledger.

**Presenter 2:**

"A vendor sees only the agreed vendor amount and its payout progress, not the client price or Elysian fee. The catalogue is structured enough for the client planner to select real deliverables instead of typing a vague vendor name."

## 15:15-19:15 | Admin Portal: Control and Commercial Operations

**Account:** Administrator

**Action:** Sign in as Admin.

### Platform cockpit

**Actions:**

1. Show the admin dashboard health and attention queues.
2. Open `Client Progress` and identify one readiness gap.
3. Open `Vendors` and `Venues` briefly.

**Presenter 2:**

"Admin sees the same operating flow at portfolio scale: event readiness, vendor verification, venue coverage, pricing gaps, inquiries, and booking status."

### Final pricing and billing

**Actions:**

1. Open `Final Pricing`.
2. Select one booking.
3. Point to vendor cost, fixed Elysian fee, final client price, and publish control.
4. Open `Client Billing`.
5. Show invoice issue state, collection entries, refunds if available, and vendor settlement state.

**Presenter 2:**

"Elysian agrees vendor pricing offline, records the vendor amount and a fixed Elysian fee, then publishes one final client price. The client pays Elysian. Vendor settlement is a separate controlled direction. The platform does not wait for an in-app quote negotiation."

### Employee roles and event scope

**Action:** Open `Team & Permissions`.

**Actions:**

1. Select the operations employee.
2. Show the role template.
3. Point to explicit capabilities such as incident management, client communication, finance visibility, and event-book printing.
4. Select the sample event.
5. Show event role, shift, and handoff notes.

**Presenter 2:**

"Clerk controls the broad portal identity. Elysian then applies a capability profile and event assignment in the database. A manager account does not automatically see every event. The administrator chooses what the employee can do and exactly which event the employee can open."

## 19:15-23:30 | Operations Portal: Manage the Live Event

**Account:** Assigned operations employee

**Action:** Sign in and open `Live Operations`.

**Presenter 2:**

"Planning is only half the problem. Once the event is live, the team needs one place for current timing, contacts, ownership, changes, incidents, decisions, and escalation."

### Assigned event board

**Actions:**

1. Show that only assigned events appear.
2. Point to function, open-item, urgent, and overdue counts.
3. Open the sample event.

### Live pulse and run of show

**Actions:**

1. Show the event header, client contact, destination, and live metrics.
2. Scroll through days and function readiness.
3. Open `Run of Show`.
4. Point to timings, venue, guests, tasks, menus, logistics calls, selected partners, and permitted finance.

**Presenter 2:**

"The command center does not duplicate the plan. It reads the same event source and reshapes it for delivery. Finance appears only for roles with finance permission."

### Incident and decision record

**Actions:**

1. Open `Feed`.
2. Create an `URGENT` incident named `Shuttle delayed at hotel pickup`.
3. Attach it to `Executive arrivals`.
4. Assign it to the operations lead and set a due time.
5. Click `Acknowledge`.
6. Explain the response, then click `Resolve`.
7. Create a `DECISION` update named `Awards entrance moved to east foyer`.

**Presenter 2:**

"The internal feed separates operations truth from external client and vendor chat. Every item keeps its reporter, severity, owner, due time, acknowledgement, resolver, and timestamps. Nothing is deleted from the live history just to make the dashboard look clean."

### Team and print

**Actions:**

1. Open `Team` and show roles, contacts, shifts, and handoff notes.
2. Click `Print event book`.
3. Scroll through cover, open attention, each day, function schedule, tasks, logistics, menus, partners, and team directory.
4. Click `Print or save PDF`, then cancel the system print dialog.

**Presenter 2:**

"The event book is generated from the same live source. It is useful as a field backup, venue handoff, or printed control-room reference. Financial details remain permission-gated in print as well as on screen."

## 23:30-25:00 | Close the Story

**Action:** Return to the operations event header, then the admin dashboard.

**Presenter 1:**

"Elysian now carries an event through one connected operating lifecycle: define the structure, compose each function, select real vendor services, estimate and publish cost, coordinate guests and timing, assign an event team, manage live incidents, and preserve a printable delivery record.

Clients see their event and complete published price. Vendors see their work and agreed payout. Operations employees see only assigned events and permitted information. Administrators control people, access, pricing, billing, catalogue quality, and portfolio readiness.

This is the current Elysian platform. A future Shobiz workflow may extend it, but that pilot is intentionally separate from this product walkthrough."

## Final Recording Checklist

- Every create or save action shows a visible success state.
- Refresh one saved client function to prove persistence if time permits.
- Never expose `.env` files, GitHub, Supabase, Clerk, Vercel, or database consoles.
- Never show vendor payout or Elysian fee while logged in as a client.
- Never claim that a payment gateway is live unless it has been separately approved, configured, and canary-tested.
- Never call proposed AI, quotation, or Shobiz-specific work complete.
- Use `event`, `host`, `client`, `function`, and `operations team` unless the selected event is specifically a wedding.
- End on the connected operating lifecycle, not a list of screens.
