# Shobiz Havas Platform Walkthrough Script

**Target length:** 14-16 minutes  
**Presenters:** Rayyan frames the problem and pilot; Kanishka operates the product.  
**Audience:** Shobiz quotation, event operations, and management teams.  
**Demo rule:** Use sample or anonymized data only. Do not show source code, GitHub, cloud consoles, credentials, or another client's data.

## Before Recording

- Create one sample multi-day event with morning, afternoon, and evening functions.
- Assign at least two venues and several vendor services.
- Add tasks, logistics notes, a run-of-show item, and one incomplete requirement.
- Publish one sample final client price and one invoice so billing can be shown honestly.
- Keep the quotation concept outside the product UI unless a clearly labeled concept screen is available.
- Close developer tools, password managers, notifications, and unrelated browser tabs.

## 00:00-01:30 | Why We Are Showing This

**On screen:** Marketing home, then sign-in.

**Rayyan:**

"Shobiz told us that three moments create the most pressure: responding to a new opportunity quickly, keeping several specialist teams aligned while an event is moving, and giving management a reliable view across multiple active projects.

This is not a promotional tour. We are going to show the current Elysian foundation as it works today, where it can already reduce coordination overhead, and which parts KARA would configure or custom-build around the exact Shobiz workflow.

The goal is not to replace the production, creative, hospitality, logistics, or commercial teams. The goal is to give those teams one current operational picture, with clear ownership and fewer manual status loops."

**Handoff:** Rayyan signs in and passes narration to Kanishka.

## 01:30-04:15 | Define an Event Once

**On screen:** Client portal, `Event Plan`, then the Definition layer.

**Kanishka:**

"Every project begins with a structured definition instead of a loose collection of chats and spreadsheets. We name the event, choose the event type, define the number of days, assign dates, and create the functions that make up each day.

Each function carries its own time window, venue, expected guest count, and required workstreams. A morning conference session, an afternoon experience, and an evening gala can therefore live inside the same event without being mixed together.

The planner turns that structure into a visual map. We can move from the full event, to one day, to one function, and then into the exact area we want to work on. That keeps the team oriented even when the event contains many days and functions."

**Demo actions:**

1. Open the event hub.
2. Select one day.
3. Select one function branch.
4. Point out date, time, venue, guest count, and requirement status.
5. Open one step token, then return to the map.

**Kanishka:**

"This is the shared source of context. A change to the function is not buried in a separate document. It remains attached to the function that the teams are executing."

## 04:15-07:15 | Turn Structure Into Coordinated Work

**On screen:** Layer 2 Food, Design, Logistics, Tasks, Notes; then Timeline and Messages.

**Kanishka:**

"Inside a function, teams work only on the sections that were selected during definition. Food can carry menu requirements and vendor services. Design can carry setup choices and special items. Logistics records arrival, load-in, transport, weather, and operating notes. Tasks carry ownership, due dates, and completion state.

Vendor selection is attached to the requirement itself. The user chooses from structured vendor catalogues and services rather than typing a vendor name into an untracked field. Multiple services can be selected where the event needs them.

The run-of-show then converts planning into execution timing. Messages remain linked to the booking and event context, so a discussion has the relevant service, date, function, and venue beside it."

**Demo actions:**

1. Open a food or design step and show a selected vendor service.
2. Show one special requirement that still needs confirmation.
3. Open Tasks and assign an owner and due date.
4. Save, close the editor, and reopen it to show persistence.
5. Open Timeline and Messages briefly.

**Kanishka:**

"For Shobiz, this shared workspace can be adapted to the departments and approval rules you already use. The value is not that every team sees every field. The value is that each team sees its responsibility without losing the common event context."

## 07:15-09:30 | Management Visibility Across Work

**On screen:** Manager Events, Manager Bookings, Admin Progress, Admin Pricing, Admin Billing.

**Rayyan:**

"At management level, the question changes from 'what is inside this function?' to 'which projects need attention right now?'

The current manager and admin views bring events, bookings, vendors, client progress, final pricing, and client collections into separate operational registers. Leadership can move from the portfolio view into the supporting record instead of reconstructing status through calls and messages.

For a Shobiz pilot, we would configure the portfolio around the stages and blockers that matter to your operating model: quotation pending, commercial approval required, client change received, production dependency blocked, or execution ready."

**Demo actions:**

1. Show the multi-event manager list.
2. Open one event or booking.
3. Show a blocked or incomplete item.
4. Show final pricing and billing as separate controlled operations.

**Rayyan:**

"Elysian records a final client price and keeps the client collection direction separate from the agreed vendor settlement direction. It does not expose private vendor payout or platform fee information to the client."

## 09:30-12:00 | Proposed Brief-to-Quotation Workflow

**On screen:** Return to the structured event definition, then show a clearly labeled concept slide: `Proposed Shobiz workflow`.

**Rayyan:**

"The next workflow is a proposed Shobiz-specific build. We are not presenting this as already complete.

The intended path is: receive the client email, brief, and attachments; extract the event scope, dates, functions, and requirements; map those requirements to approved service structures and rate rules; prepare a quotation draft; send it through the correct commercial review and exception checks; then prepare the client response for a human-approved dispatch.

The existing Elysian event structure, service catalogues, final pricing controls, and role boundaries provide useful foundations. The quotation format, rate-card rules, mark-ups, exceptions, approval hierarchy, email templates, and integrations must be mapped with Shobiz before this workflow can be built responsibly."

**Kanishka:**

"The system should improve response speed without removing commercial control. It should prepare a structured first draft, show what information is missing, and route exceptions to the right approver. A person remains responsible for the final quotation and outgoing email."

## 12:00-13:45 | What Exists and What Is Custom

**On screen:** A simple two-column slide.

**Kanishka:**

"Already built and demoable: structured event creation, multi-day and function planning, venue and vendor catalogues, requirement-level vendor selection, tasks, logistics, timelines, contextual messaging, role-based portals, final pricing, billing records, and management views.

Needs Shobiz configuration or custom development: department-level roles, Shobiz stage and readiness rules, brief and attachment ingestion, quotation templates, rate-card logic, commercial exceptions, approval hierarchy, outgoing email preparation, notification and escalation rules, and any integration with existing email, file, finance, or project systems."

**Rayyan:**

"That distinction matters. We want the evaluation to measure the real foundation, while being precise about what would be built specifically for Shobiz."

## 13:45-15:30 | Proposed Evaluation and Pilot

**On screen:** Pilot steps slide.

**Rayyan:**

"We suggest a controlled evaluation using sample or anonymized information and a small group of named users.

The first test is brief-to-quotation: can one representative brief become a structured, review-ready quotation and email with fewer manual handoffs?

The second test is event coordination: can one sample event maintain clear ownership, changes, readiness, and management visibility across participating teams?

We would measure turnaround time, manual handoffs, status follow-ups, clarity of ownership, and user feedback. If those measures show value, we would convert the selected workflow into a scoped paid pilot, then expand only after the pilot proves the fit."

## 15:30-16:00 | Closing

**Rayyan:**

"What you have seen is the Elysian foundation. The next step is not to ask Shobiz to adopt it as-is. It is to sit with the relevant teams, map the exact quotation and event-coordination workflows, and configure or custom-build the pieces that can make a measurable difference.

We would like to use the Bengaluru session to map one representative brief, one quotation path, and one live-event coordination model, then agree on the smallest useful pilot."
